# Competition Optimize

For an implementation or optimization request, deliver implemented, executed candidates and measured comparisons in the current session. Reading, planning, route names, and experiment records alone do not complete that request. When the user asks to learn a solution's thinking, first deliver its reasoning, interacting mechanisms and implications for this task; benchmarking does not answer that request. Respect an explicit research-only scope. A task adapter supplies the interface, validity checks and objective; optimize its declared metric in the correct direction.

## Start or Resume Quickly

Read the task/rules, current implementation and relevant successful/failed experiment history. Inspect the executed source and configuration of the candidate being improved, including the important code paths and pertinent prior changes. Reuse inspected code only while its identity matches. Recover unfinished work before rerunning. Reuse a verified evaluator and credible baseline with matching dependencies. Read [adapter requirements](references/adapter-contract.md) when establishing or changing evaluation; use [resume details](references/decision-loop.md) for interrupted, stale or ambiguous records.

Fix the interface, hard rules, metric/direction and development/confirmation protocol before candidate execution. Reserve confirmation/packaging resources only when an actual limit applies. Record unknown score terms. Keep candidate artifacts and results in an isolated run directory. Use existing records or a compact contract/ledger; document facts needed for reproduction, not every possible template field before doing useful work. Missing decisive rules/data may block execution; ask for that specific input and complete independent setup.

Use a bounded reconnaissance pass before expensive implementation: map the entry points and likely hot path, inspect only relevant history, and check the evaluator/contract hashes. Stop when the task model and evidence support choosing an executable mechanism, or a specific diagnostic would change that choice. A measured hotspot is one source of ideas; it does not define the search space. Do not load every old log or demand more measurements before prototyping a coherent task-derived hypothesis.

Maintain a compact candidate archive in the run directory. Keep the incumbent, the best representative of each materially different route, promising unresolved candidates, and rejected mechanisms with their evidence. Give each candidate a code/configuration fingerprint and parent IDs. Before implementing, compare the proposed change with the archive; a near-duplicate of a rejected change needs new evidence or a changed prerequisite, otherwise replace the proposal.

For a new construction that does not inherit parent code, use optional [`construction_mode=independent`](references/iteration-trace.md#declare-an-independent-construction) with `code_targets=[]`. Keep verified development parents as comparison controls and `feedback_from` as evidence; they do not require copying their implementation. Build from the task/interface in an isolated directory. Retained or combined parent components use ordinary refinement with concrete targets. The declaration does not certify novelty or hide history, and an independent result does not close the comparison parent's refinement opportunity.

Separate implementation identity from output identity. Different stochastic predictions from unchanged code/recipe are measurements of one implementation; preserve their scores and costs, and resolve consequential uncertainty under the declared repetition protocol. Improve the actual code or complete recipe next. For algorithm source plus configuration, a genuine source change can retain the same settings.

For repeated trials, use [`candidate_archive.py`](scripts/candidate_archive.py) or verified equivalent records. Start the next decision with `brief`: retrieve matched best versions, recent feedback/failures, code paths and pending proposals once, then inspect the relevant code and implement. The latest experiment is not necessarily the best parent. Check snapshots, bind the proposal to code/feedback, and record its measured successor; only evaluated outcomes count as executed changes. Use [archive checks](references/score-search.md#candidate-archive-and-route-switching) and [evidence retrieval and proposal/result links](references/iteration-trace.md) as needed.

Reconcile unfinished proposals before declaring another version of the same work. `trace --proposal-id ID` recovers the original targets and current outcome. A pending proposal belongs to its first parent's comparison; cross-contract development references supply identities and pointers that require revalidation. The driver rotates pending details after successful handoffs. Exposure alone never executes or closes a proposal: record its actual successor or a concrete reason to stop it.

In a campaign, read `trial_history` before repeating or adapting a tested mechanism. It reconnects the original basis, change and expected observation with the executed outcome, scoped feedback and source/result identities. Inspect the cited code to distinguish a missing capability from an implementation or measurement failure, then let that distinction change the next construction. The driver retrieves a recent trial related to the current/best implementation and rotates older completed trials separately from score leaders. Predictions and explanations remain agent reports; a failed run leaves method quality unresolved. A justified retry can change the implementation, prerequisite or evidence. Use exact `trace --proposal-id` retrieval when a field was shortened or omitted.

When several measured trials support a reusable conditional conclusion, record optional `--learning` on their actual prospective successor. `brief.scoped_learning` retrieves current revisions with conditions, limitations, an actionable next step and source/result evidence. Campaign handoffs keep at most one recent related report and rotate other current reports after successful complete delivery, so old conclusions need not disappear behind newer ones. Cite a used report through the next proposal's `learning_from`; update the same key with explicit `revises` when new evidence changes it. Read [conditional learning](references/iteration-trace.md#carry-conditional-learning-into-the-next-construction) for the compact input and boundaries. This is optional agent interpretation, not an automatic causal rule, score gate, method blacklist or new summarization stage.

When execution may have omitted or substituted a proposed mechanism, compare the actual successor code with its proposal and record an optional [implementation review](references/iteration-trace.md#review-the-actual-implementation). Keep fidelity separate from score and prediction support. Use its cited code and missing components to decide whether to complete, repair, preserve the actual alternative or change direction; an unimplemented component has not been tested by that result. Reviews are source-bound agent reports, not semantic proofs, ranking gates or instructions to retry every incomplete idea.

Read `review_frontier` alongside the score leaders: it retrieves explicit open opportunities across the matched development history, including lower-scoring branches outside the route list. Check their feedback and already-attempted successors before choosing a parent. A failed, unscored or explicitly unresolved child leaves the parent's opportunity open. Successful handoffs rotate exposure independently of scores; exposure does not prove value or require choosing that branch.

When adapters provide aligned case outcomes, inspect `complementary_evidence`: it retrieves executed ordinary candidates with actual wins against the best implementation, including lower-scoring versions outside recent history. Compare both source snapshots and winning/losing cases to propose a mechanism or combination, then evaluate the changed implementation. Case wins are a construction clue, not a combined score or a necessary condition for a useful prediction blend. See [case profiles](references/iteration-trace.md#retrieve-complementary-case-evidence) for identity and comparison boundaries.

Use `role=diagnostic` for an intentional development ablation or counterfactual that answers a concrete design question. Bind its first parent to the ordinary development control, preserve the executed source/result and expected observation, and use `diagnostic_evidence` or `trial_history` to inform the next implementation. Diagnostic scores do not rank contenders or count as candidate stagnation; failed diagnostics still require repair. Keep actual improvement attempts and regressions as ordinary development candidates. See [diagnostic recording and interpretation](references/iteration-trace.md#diagnostics-and-contenders) for contract boundaries and promotion.

When the adapter explicitly measures a candidate resource, inspect resource_tradeoffs for the fastest and highest-quality implementations under the same measurement protocol. Compare their code and tradeoffs to select a parent or implement a combination, then measure the successor. Missing profiles are unknown; total evaluation time is not inferred to be candidate latency. These are observed subset endpoints, not a replacement for scalar ranking or promotion. See [measured resource evidence](references/iteration-trace.md#retrieve-measured-resource-tradeoffs).

## Derive the Strategy Before Refining the Code

At initial formulation, after a consequential new source, or when continued work produces only adjacent patches, reason from the problem independently of the incumbent's functions. Describe the desired solution structure, binding constraints, available information, true cost baseline and scoring timescale. Ask what representation and construction you would choose without inheriting the current code, then compare that capability with what it actually implements. Reuse this compact model on ordinary resumptions; a supported local refinement need not repeat the exercise.

When studying a strong solution, reconstruct why its representation, construction, internal pricing, maintenance and compute allocation fit together. Identify which idea changes the attainable candidates, which components it depends on, and what the incumbent already does. Derive the heuristic from task facts before planning transplantation. A coherent structural conjecture can justify a prototype without prior measured gain; the result must still earn promotion. Use [strategy derivation and learning from strong solutions](references/strategy-design.md) for this decision, including a worked online-layout example and how to produce genuinely distinct routes. Its [source-backed generation patterns](references/source-patterns.md) give concrete mechanisms and cautions. Keep the useful reasoning in existing notes rather than creating another required report.

## Continue Without Default Caps

Do not impose default limits on total time, compute/cost, candidate count or rounds. An optimization request authorizes ordinary local research, implementation and evaluation; continue useful feedback-driven iterations without asking for renewed permission between trials or batches. Record actual time/compute/cost and evaluated variants, including baselines, failures, repairs and unchanged repetitions. Accounting is evidence for efficient decisions, not a quota.

A single conversation turn cannot guarantee an unattended long campaign. When the user requests autonomous continuation, use the [durable campaign runner](references/unattended-campaign.md) after establishing the task adapter and development archive. Its background supervisor relaunches completed turns, preserves session/evidence pointers and reconciles interrupted work. In an open-ended unattended campaign, complete/blocked receipts are advisory: a plateau or exhausted route triggers a fresh strategy and an executable successor. Only the configured task verifier, a user stop, an explicit resource limit or an observed host/evidence blocker ends the campaign.

Inside a driver-managed invocation, finish an archived implementation/evaluation step and return the structured continuation receipt as a checkpoint. The outer loop executes the follow-up; returning that receipt does not end the campaign. Do not keep one invocation open solely to avoid stopping.

The driver injects a bounded development evidence packet into every invocation: matched historical bests, failures, unresolved branches, pending work and code/result identities. Use it to choose a parent and inspect the cited evidence; old conversation summaries and feedback explanations can be stale. A failed, invalid or unscored execution enters repair with verified result diagnostics and an available scored reference. Diagnose the responsible implementation, data, environment or measurement path; an unscored result does not disprove the method. Repeated missing observations trigger a fresh repair review. Failed invocations do not consume its review checkpoint. Configurable objective reviews and periodic fresh contexts preserve history without imposing a candidate allowance. These triggers do not certify a plateau or replace the task's promotion protocol.

Changing evaluation contracts can leave each implementation with only its own baseline. `comparison_continuity` tracks newly observed contracts that still lack a different measured implementation, even when healthy smoke runs intervene. A fresh `measure` review supplies the isolated target, contract differences and source/result pointers in `comparison_recovery`. Inspect that target, select an existing legal common development contract, and measure a trusted reference and candidate under it. Genuine new measurements may reuse archived code/recipes with a reuse reason; compare scores only after complete contracts match. Preserve the fixed evaluator and confirmation boundary. Legitimate fidelity exploration can continue; the trigger requests missing evidence. A successful handoff records the sealed observation checkpoint, while actual matched measurements resolve the gaps.

If `repeat_conflict` reports a same-contract ordering reversal, inspect its verified leader, challenger and witness, then archive a task-specific paired plan with `candidate_archive.py measure-plan` before more runs. Predeclare run/seed identities, repetitions and the decision rule. Use `measure-status` to resume unmatched slots and attach the plan/run IDs plus exact seeds/repetitions to each adapter result. After completing the pairs, interpret the declared rule and persist the conclusion with `measure-decide`. If the frozen protocol cannot be completed, use `measure-stop` with a reason and concrete next action; retain incomplete evidence and continue a feasible repair or alternative. Changing source/recipe cannot fill the original plan's slot. Do not select lucky repeats or automatically replace the best with an informal mean. See [repeatability plan semantics](references/iteration-trace.md).

Honor competition hard rules, actual resource availability and any limits the user currently specifies. Apply a user's later removal or change of optimization limits prospectively; preserve earlier consumption and evidence. On resumption, distinguish these applicable constraints from obsolete skill defaults and agent estimates. Record no self-imposed cap when none applies; do not require a numeric allowance, create a replacement cap or stop because a historical default was spent. Under a genuine finite constraint, plan confirmation/packaging resources from measured costs.

## Incorporate User Ideas

Accept free-form ideas, intuitions, domain observations, links and code sketches at the start or during iteration. Preserve the user's intended mechanism and distinguish a suggestion, an explicit request to test it, a hard requirement and a request for discussion only. In an active optimization request, a feasible suggestion should enter the implementation decision rather than receive only an acknowledgment or a plan. Do not require the user to supply code or prove the idea first.

Connect the idea to task structure, relevant code and matched history, state assumptions briefly, and turn it into the smallest complete falsifiable candidate or diagnostic when implementation is requested. A request to understand a linked solution calls for mechanism learning before migration tests. Honor an explicit test/priority request within competition rules; otherwise compare it with the strongest feasible alternative and explain any deferral. Keep the user's idea distinct from the agent's interpretation and measured evidence. Use the existing proposal/notes to retain its origin and result; follow [user-idea handling](references/score-search.md#turn-user-ideas-into-experiments) for ambiguous, previously tested or mid-run input.

## Repeat the Feedback Loop

Initialize the best development candidate from the credible baseline. Repeat steps 1-5 until an actual stopping condition applies. A completed trial returns to step 1; a driver-managed invocation returns its checkpoint so the driver can continue. Do not wait for another user prompt between trials. If the next implementation is unclear, revisit the formulation or obtain the specific missing evidence.

The default is agent-developed implementation changes informed by task structure, user ideas, strong solutions, code and history. Do not schedule grid/random/Bayesian parameter searches, neighboring-value sweeps or seed hunting. Dedicated parameter tuning requires an explicit user request. A supported mechanism may change internal settings as part of its implementation; changing a list of values alone does not establish that mechanism.

Use exploration and exploitation deliberately. Exploit a supported unresolved mechanism; when comparable refinements have weak returns, revisit the actual score headroom and limiting representation using [plateau recovery](references/plateau-recovery.md). A low score, runtime hotspot or loose upper bound does not demonstrate recoverable points. Test a complete alternative from an appropriate historical parent or simpler baseline when warranted; a new route need not guarantee a large gain before a prototype is useful.

1. **Propose from task structure and evidence.** Compare the incumbent's capabilities with an independently derived formulation, applicable reference mechanisms, user ideas and matched results. Name the missing capability or supported refinement. Prioritize hard feasibility, user-directed tests and objective headroom. Keep one compact proposal: task/source basis, parent/code target, pertinent history, mechanism and coupled components, difference from rejected attempts, expected observation, validation and cost. Link it from other notes instead of copying it. Use the [proposal and quality gate](references/score-search.md#efficient-proposal-and-quality-gate); resolve a specific knowledge gap when needed, then implement within the authorized scope.
2. **Implement the chosen change.** Name the parent, concrete implementation target, expected observation and planned cost. Favor a complete alternative algorithm/representation, model/training pipeline or policy over repeated adjacent settings, caches or cleanup passes when substantive headroom warrants it. Implement necessary coupled components together. Keep an evidence-supported refinement when worthwhile; a route name does not make a local patch a different method. Valid outputs may differ from the incumbent.
3. **Run and compare.** Pass the candidate through the [quality gate](references/score-search.md#efficient-proposal-and-quality-gate), then compile/train/execute at matched fidelity, preserving source/configuration, commands, results and validity evidence. A mechanism diagnostic, full development comparison and final confirmation answer different questions; do not confirm or package every positive proxy delta. Compare with the parent and current best under the declared objective, including resource costs. Check shared-machine interference before consequential timing; preserve valid deterministic quality evidence when only timing needs remeasurement. Separate partial/invalid runs from valid low scores; reduced fidelity cannot establish a full-score winner.
4. **Turn the result into feedback.** State the observed gain/regressions, relevant errors or bottlenecks, and whether the prediction was supported, contradicted or unresolved. For a user idea, connect the tested interpretation and result back to it and say what follows; do not imply an untested interpretation was disproved. Update the candidate archive and failure mechanism index. Keep causal explanations provisional unless tested. Decide promotion separately from further investment: update the best only with eligible evidence; retain useful alternatives. Choose repair, measurement, deepening, route replacement or combination using [feedback rules](references/score-search.md#close-the-feedback-loop).
5. **Execute the follow-up and honor actual stopping conditions.** Link the feedback to the next specific code/pipeline change, its parent and expected observation. Return to step 1 and implement it, or return the driver checkpoint after this invocation's archived step. Missing evidence warrants a targeted diagnostic or search that produces a next implementation decision. Stop when the user asks, an applicable hard/resource constraint prevents further work, a concrete blocker cannot be resolved, or the declared completion condition is verified; then freeze/confirm/deliver as feasible. A weak score, one patch, a list of ideas, a completed batch or a lack of new ideas calls for reassessment rather than ending an open-ended campaign.

## Select by the Actual Objective

Enforce competition/user hard limits. Do not invent universal minimum gains, maximum slowdowns, statistical-significance gates or output-equivalence requirements that replace the objective. Agent-chosen screens are provisional search policies, not contest rules; state their basis and revise them prospectively when they exclude useful comparisons. Do not retrospectively change a frozen delivery rule from confirmation feedback.

If score terms are missing, preserve raw components and tradeoff candidates, label proxy choices provisional, and identify what could reverse selection. Check available platform feedback for proxy-ranking contradictions and whether improvements affect a score term's effective range; further local repetitions cannot identify missing official terms by themselves. A small gain may be real; a quality/runtime tradeoff with unknown score parameters cannot establish a net loss. Resolve consequential measurement noise using applicable resources.

## Confirm and Deliver

When stopping for a stated reason, freeze finalist artifacts and the delivery rule before independent confirmation. Keep final tests out of tuning. Verify selected validity, resource checks and package bytes. Report any check that a concrete blocker or actual resource limit prevents.

Deliver runnable artifacts, baseline/candidate metrics with provenance, real changes, cost, reproduction commands and remaining uncertainty. Include the candidate archive summary, repeated-change checks, route switches and compact iteration trace: measured result -> feedback decision -> actual successor/change -> new result or stated stop. Mark unexecuted follow-ups as pending, never as completed progress. If nothing improved, report that outcome with executed alternatives or the concrete blocker. Official submission/upload requires explicit user authorization.
