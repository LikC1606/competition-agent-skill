# Competition Optimize

Optimize the declared competition objective: maximize a higher-is-better score or minimize a lower-is-better metric. Use measured results to decide what to try next. The core controls experiment selection and budget; an adapter supplies the task's representation, rules, evaluation, and diagnostics. Execute the workflow in the current Codex session.

## Workflow

1. **Seal the task and resume existing work.** Identify the family, candidate format, rules, hard constraints, resource limits, official metric/direction/formula/aggregation, available data/tests, submission limits, and the user's budget. Declare the confirmation shortlist limit, fallback, and decision rule for ties or disagreement with development. For a new run, create `<competition-workspace>/agent-runs/<UTC>-<slug>/` outside protected test/data directories, with `task-contract.json`, `research.md`, `trials.jsonl`, `candidates/`, `evaluations/`, and `comparisons/`. For an existing run, read its contract and latest ledger entries first. Keep unknown score terms explicit; resolve ambiguous hard rules and metric direction before costly search.
2. **Verify the scoring path.** Read [the adapter contract](references/adapter-contract.md) and use or build the task adapter. Compare the rules, scoring implementation, and returned fields: verify the direction, units, aggregation, timeout behavior, and what validity actually covers. Check known-good and known-bad candidates. Freeze the evaluator, development workloads, and confirmation protocol; a necessary correction requires a new contract version and reevaluation of compared candidates. Distinguish local official-metric calculations, proxies, and platform results.
3. **Research and establish a baseline.** Read the relevant section of [the task-family guide](references/task-playbooks.md). Search using the objective, input structure/scale, constraints, and likely bottleneck; prefer primary writeups, papers, official tools, and inspected source. Turn useful findings into hypotheses with prerequisites and a cheap transfer test. Reuse a valid existing baseline when its artifacts and evaluation still match the contract; otherwise build and measure one. Establish validity and reproducibility before score search. Record whether the baseline is a pipeline sanity check or a credible scoring reference; improvement claims need the latter. Save immutable artifacts, exact commands, hashes, logs, and results.
4. **Allocate the budget from measured cost.** Reserve final confirmation and packaging first. Use baseline costs to allocate research, diagnostic experiments, route exploration, component refinement, and combinations. Without an explicit budget, run an initial batch of at most three candidate trials plus final verification; choose distinct mechanisms or deeper refinement according to the evidence. Code/configuration variants, including ablations, repairs, and rejected candidates, consume trial slots; repetitions consume time/compute under the adapter's declared protocol. An explicit larger budget permits more batches. Keep the final reserve available.
5. **Choose, execute, and learn from trials.** Read [the search protocol](references/score-search.md). Select an action from the current uncertainty: explore a route, diagnose a bottleneck, refine a component, tune a demonstrated mechanism, or combine complementary candidates. For each trial record parent IDs, the target component, hypothesis, predicted observation, cheapest rejection test, and cost before implementation. Keep incumbent and promising alternatives immutable. Screen cheaply, evaluate promising candidates at matched full fidelity, and append the evidence and decision. When a few cases or seeds can reverse a close ranking, check stability before finer tuning. Within a promising component, use prior results to choose the next variant; switch when measured gains or credible mechanisms run out. Keep observations, explanations, and next tests distinct.
6. **Promote and confirm.** After the required hard checks pass, promote by the declared objective at matched fidelity; slower execution or a soft-component regression may be acceptable when the total score improves. If score terms are missing, preserve tradeoff candidates and label proxy-based choices provisional. Use development evidence for tuning and separate data/seeds for confirmation; never tune on an official final test set. Repeat noisy comparisons, and treat unresolved differences as unproven. Freeze finalist identities, pipeline/recipe hashes, and the delivery rule before spending the confirmation reserve. Apply that rule even when rankings reverse; report the disagreement and any need for fresh evidence.
7. **Deliver the selected artifacts.** Stop at the budget, or when no credible new experiment fits outside the reserve. Verify the selected candidate's rules and package bytes. Report baseline and best confirmed metrics with direction and provenance, material trial results, cost, exact reproduction commands, artifact/evaluator/data hashes, output paths, and remaining uncertainty. Retain task-qualified lessons with their evidence for future runs.

Reuse an evaluation only when candidate, evaluator, score model, data/split, configuration, and relevant environment hashes still match. On resumption, an unfinished trial may be repaired within budget or classified as interrupted; it is never an evaluated best. Do not start an independent run for the same task unless requested.

## Adapter Routing

- For the fixed-timeslot C++ case, read [the fixed-timeslot adapter reference](references/fixed-timeslot.md).
- For unweighted scalar regression or binary-classification CSV predictions, read [the local prediction tools reference](references/data-model.md). The scripts check artifacts, compute local metrics, estimate paired sampling uncertainty under explicit row/group assumptions, diagnose development errors and slices, and construct fixed-weight blends. Use diagnostics to form the next hypothesis and reapply frozen recipes on confirmation/test predictions. Establish member model identity, training, leakage, and ensemble resource checks separately before promotion.
- For data/model, algorithm/optimization, or stochastic simulation tasks, read only the applicable section of [the task-family guide](references/task-playbooks.md) when selecting baselines and improvement mechanisms.
- For any task family without a verified adapter, establish its score contract and evaluator before expensive candidate search. Do not imply that this repository already implements every family.

Do not upload, submit, publish, or consume official submission quota unless the user explicitly requests it. Do not run unbounded loops. Avoid parallel evaluations when they can distort timing or resource measurements; use them only when the evaluator controls those effects and the budget allows it.
