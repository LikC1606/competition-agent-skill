2026-11-16。依据[专业比赛 Skills 与 Agents 研究报告](competition-skills-agents-research-report-2026-11-16.md)，对照 `competition-optimize` 的实际实现制定。方案基线为 `fde9ea880d2de2602d64ca10e730212ceb785303`。A—C 阶段已实现，范围搜索、榜单关联、方案帖、评论和 notebook 历史版本已完成线上验证；API token 认证及读取器自动加载凭据也已通过。后续传输故障已加入 gzip、有限重试和显式连接选项，三条受影响链路复测通过。具体测试及版本翻页等验证限制见[实施记录](competition-improvement-implementation-2026-11-16.md)。

## 1. 改进目标与总体选择

建议采用**一个专业资料读取入口，加上贯穿五个方向的完整示例**。新增代码集中解决已经确认的操作缺口，其余改进接到现有研究、评测、提案、实现复核和条件经验链。

目标是让 agent 更容易完成这条实际路径：

> 找到可靠且相关的原始资料 → 解释强方案的能力与条件 → 对照当前实现定位缺口 → 排除理论上无效的改动 → 实现完整机制 → 用匹配评测判断结果 → 据此选择后继。

沿用用户已经明确的要求：主动查专业资料；重视本地评测；避免按公榜反复择优；改动必须有理由；默认进行机制改进；优先理论、源码和已有产物分析以减少无效实验。方案编制不启动训练、模型调用或比赛提交。未来实现时，软件接口的必要测试与比赛提分实验分开验收。

2026-11-16 用户确认的后续成熟度验收目标是：换到陌生比赛后，自主完成资料获取与核实、可信本地评测设计、有依据的机制实现、结果分析与后继选择，尽量减少人工接管。目标及证据边界见[决策 0001](../research/decisions/0001-autonomous-workflow-acceptance.md)。本方案 A—C 的软件交付记录继续有效；完整流程自主性与跨任务效果仍按实际证据判断，具体通过门槛尚未确定。

用户随后要求补充已识别的三个缺口，现已接入主 skill、相应参考指南与每轮提示：来源主张回到保存版本的具体原文；实施前检查等价性与实际流水线机制；恢复并维护开发选择已使用的反馈边界。复用 `basis`、任务笔记和后继反馈，保留密封历史。软件与独立 DeepSeek 场景验证的结果、覆盖范围和限制见[实施记录](competition-improvement-implementation-2026-11-16.md)。

| 方向 | 当前已有基础 | 这次建议的具体增量 |
| --- | --- | --- |
| 更会查资料 | 已有问题驱动的 Search→Read→Pivot、来源链和迁移要求 | 增加 Kaggle 只读入口，处理真实比赛、榜单关系、全文/评论和指定代码版本；把输出接进 `research.md` 与 `basis` |
| 高质量本地评测 | 数值表格已实现逐折 fit、OOF、group/time 检查、冻结交付 | 增加一个从任务信息边界到实际训练与证据失效范围的完整案例；其它题型按真实任务补 adapter |
| 不过拟合公榜 | 已有公榜分歧诊断和独立确认规则 | 增加一个公榜与本地冲突的决策案例，说明何时修评测、何时保留未决，以及哪些动作会污染确认 |
| 有依据改进 | 已有 proposal、implementation review、条件 learning 与后继引用 | 给出一条从原始资料到提案、执行解释和后继的完整例子，明确依据如何改变实现 |
| 机制级改进 | 已有独立任务推导、完整机制与必要耦合要求 | 增加真实行为变化、等价变化和机制未落地的对照案例，用已有字段表达判断 |

这个建设顺序不改变比赛中的路由优先级：若当前比较本身不可信，仍先修评测；若机制和依据已清楚，就进入实现，无需为使用新工具再查一轮资料。

## 2. 第一项：Kaggle 原始资料读取入口

### 2.1 接口与责任

新增 `skills/competition-optimize/scripts/kaggle_sources.py`，只承担资料的发现、读取和本地保存。它不决定方案优劣，不运行下载的 notebook，不产生候选分数。

以下命令已实现，选项与范围见[工具指南](../skills/competition-optimize/references/kaggle-sources.md)：

```sh
/usr/bin/python3 skills/competition-optimize/scripts/kaggle_sources.py discover \
  --competition COMPETITION_SLUG \
  --question "当前要查明的验证或机制问题" \
  --output-dir /absolute/task/run/research/discovery-01

/usr/bin/python3 skills/competition-optimize/scripts/kaggle_sources.py read \
  --url SOURCE_URL \
  --output-dir /absolute/task/run/research/source-01
```

`read` 按实际对象读取 writeup、topic 或 notebook。对 notebook 区分版本号与 URL 中的 session ID，显式参数冲突时直接报错。评论可以展开本地已保存内容，或显式指定服务端请求范围；已在线验证指定部分评论 ID 可取得其正文及嵌套回复，完整分页规则仍未确立。本地全文显示不代表全部历史。

实现参考 shepsci 的公共 Kaggle MCP 读取路径及精确比赛 scope、榜单关联和全文处理思路，指定 notebook 版本参考 NVIDIA 的归档路径，采用一个标准库客户端。线上验证后，HTTP 404 已定位到代理路径，部分评论占位已正确处理；全站搜索的比赛过滤实测未生效，发现入口已改用真实比赛 `forumId` 对应的论坛搜索，并支持 `--search-page` 显式翻页。上游出处与其余验证边界见工具指南、研究报告和实施记录。

### 2.2 发现资料：保留真实关系

- 先解析精确比赛身份。按比赛过滤的结果与全站关键词搜索保持不同身份；返回实体的真实归属不能仅由请求参数填入。
- 榜单 writeup 按真实 team/board 关系关联，保留 public/private 榜单来源；普通搜索不补造排名。
- 问题决定阅读次序：验证失配优先查规则与 validation 讨论，机制缺口优先查完整方案及匹配实现。排名、票数和时间只是发现信号。
- 本赛资料不足时沿现有指南查询相邻任务和论文，明确类比条件。资料读取工具只负责取得内容，查询如何转向由当前研究问题决定。

### 2.3 阅读正文与纠正：明确读到了多少

输出需要能区分以下事实，而不是给出笼统的“读取成功”：

| 信息 | 需要表达的语义 |
| --- | --- |
| 正文 | 原始正文及可读文本；显示是否截断、如何继续读 |
| 评论/回复 | 实际已取得和已展示的范围、可继续展开的位置；未知总量保持未知 |
| 错误 | 哪次详情、评论或版本请求失败；请求失败不能转换成“没有相关内容” |
| 缓存 | 此次内容来自哪个快照、何时取得、是否真正刷新了相关部分 |
| 来源关系 | 真实 URL/ID、比赛身份，以及有依据的排名或版本关系 |

可读输出保持紧凑，但必须暴露重要缺口。比如主帖支持某方法，而未展开回复中可能有纠正，agent 应知道评论尚未读完，并能定向展开。`full` 只表示本次响应未在本地裁切，不能暗示服务端所有历史已穷尽。

### 2.4 代码版本：严格对应请求

请求历史版本时，保存请求版本与实际取得版本。版本无法确认或无法取得时，返回明确的未满足项；不静默换成 latest。只有当前研究需要 latest 时才读取 latest，并标出实际版本身份。

首次实现不扫描全部历史版本，也不按 best-public 自动选研究代码。解释一篇强方案时，先取作者实际引用的版本；是否比较版本历史由研究问题决定。

### 2.5 保存与现有提案衔接

资料写到当前任务的 `<run>/research/`，不写回本仓库的竞赛知识目录。使用普通 JSON/Markdown 保存原始响应、可读正文、必要元信息和源码快照；保留可引用的文件路径与字节 hash。缓存按真实来源与版本区分，刷新保留旧快照，后续只展开缺少的部分。

现有任务 `research.md` 只记录与决策相关的内容：当前问题、关键原文定位、真实 URL、已保存快照及版本、适用条件、未决点和下一步。原始来源与 agent 的解释分开。

提案继续使用现有字段：

| 字段 | 来源研究如何进入 |
| --- | --- |
| `basis` | 引用原文和本地快照；说明来源提供的能力、当前父代码的差距与迁移条件 |
| `change` | 写明实际要改的机制与必须一起实现的部分 |
| `expected_observation` | 给出能区别新旧方法的行为，以及可能不成立的条件 |
| `validation` | 说明哪些已有证据、理论分析或后续比较能回答剩余问题 |

不新增 `source_ids`、提案类型或候选账本。现有 archive 不会自动核实 `basis` 的来源语义；新入口提供可读、可回查的证据，也不将 hash 当作语义正确或因果成立的证明。原创任务推导仍可直接作为依据，无须强行附加一篇资料。

## 3. 第二项：把本地评测设计写成可操作案例

在 `references/local-evaluation.md` 增加一个完整案例，链接已有 `tabular_training.py`、划分检查和训练 pilot。这里补的是使用方法，复用已有训练实现。

建议案例设定：**目标为预测未来新实体，标签存在延迟**。案例应顺着以下路径讲清楚：

1. 根据真实任务确认“新实体”和“未来”的含义；若实际目标是已知实体的未来行为，则不能机械使用新实体 holdout。
2. 推导每折训练/验证 ID、事件时间、标签可用时间和必要间隔。仅保存 fold 标签不能表达全部时间训练边界。
3. 让实际 estimator/预处理只在训练折拟合，验证折仅用于预测；检查上游特征是否符合相同信息边界。
4. 发现协议错误后，先记录任务依据和修订原因，再看新排序；旧 OOF/模型分数不能继续为新协议下的晋升背书。
5. 只重建受影响且当前选择需要的对照。资料、源码逻辑和未受影响的检查可继续复用，不要求重跑全部历史。

同时示范三种结论的区别：手算或已有产物可以排除信息越界；机制探针可以判断行为是否发生；代表性开发比较才支持候选排序。增加 seed 不能修复错误单位或未来标签泄漏。

这一改动的验收是读者能从任务条件推导实际边界，明确哪些证据仍可用。新增文字不需要字符串匹配测试，也不需要为编写案例运行一次训练。

## 4. 第三项：公榜分歧与确认污染的处置案例

在现有公榜分歧段补一个“候选公榜升、本地降”的案例，不另建榜单控制器。

| 发现 | 应采取的行动 | 对当前选择的含义 |
| --- | --- | --- |
| scorer、输出对齐或真实推理实现确有错误 | 修正负责层，保留旧评价身份，在新协议下建立必要对照 | 原比较受影响，不能只替获益候选换分 |
| 官方事实或数据结构支持目标分布/信息边界失配 | 在看新排序前说明修订依据，或提出针对该差距的机制 | 修订由独立事实支持，不能倒推 folds 追榜 |
| 只有一次榜分变化，原因仍不清楚 | 保留分歧与解释，不因该次公榜晋升候选 | 继续按可比本地证据工作 |
| 冻结后看了确认错误，再据此修改 | 将这些反馈视为已参与开发，后续沿任务实际允许的交付规则处理 | 不继续宣称原确认独立，也不自动要求更多昂贵运行 |

案例要同时说明：反复在本地开发集取最大值也可能偏向噪声；把选择搬到本地并不自动解决自适应过拟合。历史强队排名帮助找资料，当前公榜变化是当前开发反馈，两者的用途不同。

不新增固定提交次数、显著性阈值或最低涨分门槛。正式提交与上传继续遵守现有授权要求；资料只读操作不因此增加审批步骤。

## 5. 第四项：贯通一条有依据的机制改进案例

在 `references/competition-research.md` 和 `references/strategy-design.md` 中补一条互相链接的案例：前者展示来源如何进入提案，后者解释能力、行为和必要组件。`iteration-trace.md` 只在需要时补来源引用示例，沿用现有 review/learning 用法。

### 5.1 正例：从短工序优先到考虑就绪状态

用研究报告中的 JSSP 源码作素材，但明确**案例假设父实现按下一工序耗时排序，不代表当前已选定比赛或已证明新规则更优**。

| 环节 | 案例应写清的内容 |
| --- | --- |
| 原始依据 | 已读代码使用机器与 job 的就绪时间；引用对应固定源码，而非只记算法名 |
| 父实现缺口 | 当前假设中的排序只看耗时，不能利用已有就绪信息区别两项任务 |
| 机制假设 | 将可观测就绪状态用于构造选择，可能减少特定状态下的等待；完整目标收益仍未知 |
| 必要组件 | 正确维护并读取机器/job 状态，改变实际排序，再由合法操作更新调度；修改函数名不算完成 |
| 区别新旧行为 | A 耗时 1、就绪 100；B 耗时 10、就绪 0。两种规则会选不同任务 |
| 反例风险 | 更早开始未必带来更短终局 makespan，可能推迟关键路径或稀缺资源上的工作 |
| 剩余证据 | 手算可验证行为差异；若以后实施，合法性与完整目标比较仍由任务 evaluator 提供 |

这个例子要让 agent 学会从可用信息推导改动，并同时说明为什么可能失败。原方案的完整分数不能证明其中每个组件都值得迁移；案例也不应凭空承诺涨分。

### 5.2 执行后如何解释，不只写“成功/失败”

| 实际情况 | 使用现有证据的方式 | 后继 |
| --- | --- | --- |
| 代码没读就绪状态，排序仍等价于父版 | `implementation_review` 指明实际机制与缺失部分；仍保留真实运行成绩 | 判断该机制是否仍值得补做，不将其写成已被性能否定 |
| 改动真实发生，但操作不合法或运行失败 | 保留失败与执行证据，进入 repair | 先修实现；不把无效运行当有效低分形成学习结论 |
| 机制完整、运行有效，但目标退步 | 对照原假设和失败场景，按既有条件学习记录适用范围 | 重审迁移条件或改另一能力，不自动扫相邻系数 |
| 新候选在可比开发协议下改善 | 保留真实源码、结果、代价和退步场景，独立判断晋升与后续投入 | 有用结论通过 `learning_from` 进入后继提案 |
| 机制明确，只有排序仍影响选择且不确定 | 先复用已有结果；必要时沿现有配对测量计划补证据 | 不挑幸运重跑，也不固定要求多 seed |

忠实度、成绩与解释分别判断。偏离原提案但实际更强的候选仍可按分数比较；实现忠实也不自动晋升。学习结论保持条件与限制，不能根据一个结果建立永久路线黑名单。

## 6. 第五项：把理论分析用于排除无效改动

在 `strategy-design.md` 或已有 `source-patterns.md` 中加入一个正反对照，复用上节案例，避免维护多份重复教程。

| 拟议改动 | 不花训练成本先分析什么 | 应得到的判断 |
| --- | --- | --- |
| 对所有动作减同一个全局偏置，再取最小值 | 化简排序：通常精确算术下 `argmin(a_j-c)=argmin(a_j)` | 此项不改变选择，调偏置不能提供声称的新能力 |
| 使用机器/job 就绪时间代替仅按耗时排序 | 在同一可行状态手工比较动作，并追到实际选择代码 | 确实改变信息使用与动作；性能尚未证明 |
| 新增状态特征或选择器 | 追踪输入、调用与实际输出，核对推理时是否取得这些信息 | 未接线或不可用的信息不能算能力已实现 |
| 移植强方案的一个组件 | 检查表示、目标、数据组织与推理的必要依赖 | 残缺移植的低分不足以否定完整机制 |
| 给同批多个想法都记总涨分 | 检查每个想法实际对应的父版、改动和比较 | 总收益不能自动归因给每个想法 |

这些判断由 agent 对具体机制负责，不增加通用“创新分”、代码行数门槛或自动语义判定器。理论分析的出口是：排除已证实等价/不可行的方向，修正缺失的机制，或形成值得实施但收益未决的完整假设。

也不把理论分析变成固定前置大作业。已经有清楚依据、行为和可用评测的局部机制，可以直接实施；只有会改变当前决策的未知点才值得继续分析。

| `references/iteration-trace.md` | 必要时补来源进入 `basis`、结果进入 review/learning 的短例，复用已有字段 |
| `SKILL.md`、`README.md` | 增加按需入口与能力范围说明，不将所有用法塞进每轮上下文 |
| `scripts/campaign_prompt.py` | 仅在实际交接缺少发现入口时补一条条件提示；已有引用足够则不改 |

表中 `scripts/`、`references/`、`tests/` 均位于 `skills/competition-optimize/`。资料工具产生的任务材料保存在运行目录，与技能源码分开。

保留 `candidate_archive`、`implementation_reviews`、`scoped_learning`、现有训练 adapter、纯策略和恢复接口。读取一次资料不计作新实现，不重置停滞信号；引用来源也不改变比较身份或候选晋升规则。旧档案可继续使用，无需迁移。

## 8. 实施顺序与低成本验收

### 阶段 A：完成只读资料入口

先确认实际支持的接口，完成 discover/read、保存、展开与错误语义，同时写必要的固定响应测试和使用说明。测试应围绕已发现的行为风险：

| 场景 | 必须能观察到的结果 |
| --- | --- |
| 同名或近似标题、实体实际属于另一场比赛 | 不将请求方标签当真实归属；未核实项可见 |
| 榜单关联与普通内容搜索 | 真实 join 保留来源，fallback 无虚构排名 |
| 主帖完整、评论显示截断或上游只返回部分 | 已读范围与继续展开入口可见；展开可取得固定响应中的关键纠正 |
| 主帖成功、评论失败；或缓存中已有旧正文 | 部分失败和缓存来源可见，不用“已刷新”掩盖缺口 |
| 指定 notebook 历史版本与 latest 内容不同 | 得到指定版本，或明确未满足；不静默切 latest |
| HTTP 成功但服务返回工具错误，或响应格式变化 | 返回实际失败，不把错误解析成无结果 |

这些是来源能力的验收，不要求训练。实现时再用实际只读来源确认 live 路径；服务不可访问时准确报告哪些能力只完成了离线验证。

### 阶段 B：完成贯穿五个方向的案例

按第 3—6 节补充指导。人工走读案例是否能回答：资料影响了哪个决策？边界修复使哪些旧证据失效？公榜冲突时依据是什么？新机制在哪里改变行为？结果会如何改变后继？

案例用手算、源码和现有产物即可完成。它们是教学与决策示例，不伪造候选、榜分、实验记录或学习报告，也不需要为文字增加实现镜像测试。

### 阶段 C：接通按需使用并完成交付

更新入口和交叉链接，确认研究结果能直接引用到原有 proposal。只运行受改动影响的软件测试；若确实修改 campaign 提示或交接，再运行对应本地回归检查。没有 driver 行为变化就不扩大到 campaign 实验。

这一轮建议的实施范围是 A—C。交付应包括可调用工具、范围清楚的读取结果、文档与完整案例，以及实际测试/只读接入结果；明确未验证的 live 能力和竞赛收益。

### 条件性后续：真实题目的 adapter

若下一场比赛需要图像、文本、特殊计分或远程训练，再选一个具体任务，复用现有比较与档案合同实现实际执行。保留真实训练边界、checkpoint/输出、官方聚合和冻结交付。这部分由实际任务触发，不纳入当前通用资料入口的完成条件。

## 9. 成本与采用边界

软件验收主要花费本地解析、文件保存和必要的只读网络访问；agent 阅读和分析会消耗上下文。它们不需要 GPU，但不是“零成本”。请求数、耗时、响应大小等按实际取得的信息记录，不用未知单价计算出一个虚假的零费用。

采用时遵循三个取舍：

- 按问题展开资料，复用仍适用的快照；避免默认扫全站、全部评论和全部历史版本。
- 用原文和源码形成机制解释，复用现有档案；不增加常驻 researcher、独立总结模型或跨比赛向量库。
- 先解决接口正确性与决策可用性，真实提分和训练成本变化保留为后续任务问题，不设默认大型评测 campaign。

本方案预期改善的是取得专业证据、识别无效方向和衔接机制实现的能力。当前能明确验收这些软件行为与案例逻辑；不能仅凭方案或接口测试，承诺比赛分数提升。
