# 实际使用复盘与执行流程修正

2026-10-10，用户测试 `competition-optimize` 后反馈“只分析或小改，没有实质推进”。本次依据真实对话与运行记录修正主流程，未增加脚本 pilot，也未重新执行额度已经耗尽的比赛实验。

## 观察到的问题

对话“查看所指内容”的本地运行 `agent-runs/20261010T093542Z-timeslot-resume` 保存了两轮报告、版本化契约和候选记录。用户曾明确追加 3 个和 6 个候选；9 个额度全部使用，保留 v17，没有发布 v18，没有 challenger 进入独立确认。

| 实际投入 | 开发结果 | 能说明什么 |
| --- | --- | --- |
| 三个等价加速变体：区间抵消、代价表布局、起点缓存 | 最好线程周期减少约 0.62%，未达到自定 2% 门槛 | 执行过代码，但没有测试不同的完整解题方法 |
| 互换复原清理 | 两种规模的质量代理 C 增加 0.00020056，线程周期增加约 9.68% | 存在质量/速度取舍；超过自定 5% 减速上限后未确认 |
| 双向窗口、短区间轮转及一次缺陷修复、两种删除代价缓存 | 其余有效变体未提高质量，缓存仍变慢 | 多数是原优化器的组件改动；缺陷不能当作有效方法评测 |

这些记录说明 agent 做过实验。用户感到没有实质推进的原因包括：旧默认三个候选被当成任务永久额度，继续请求反复触发额度询问；路线名称掩盖了局部改动；代理门槛排除了进一步比较。已有 v17 的一个本地最慢 workload 约 1.71 秒，而官方规定 1.5 秒，实际测量边界和硬件不同，仍需优先解决可行性风险。

官方速度项的 `tfast`、`tslow` 与跨用例聚合缺失。质量代理 `C = 0.55 mean(U) + 0.35 mean(V)` 和线程周期变化不能推出官方净分数，因此不应把自定减速上限解释成官方分数损失。历史规则、结果及用户明确授予的 3/6 个额度保持原样；本次不追溯更改选优结论或扩大该运行的额度。

## 已修改的行为要求

1. 优化请求以实现、执行和实测对比为交付；先复用可信 evaluator/baseline，仅记录复现与决策必需的信息。
2. 用限制得分的机制选择完整可执行方法。必要组件一起实施，弱结果后继续下一项值得投入且预算容纳的实现；缓存、筛选窗口、清理步骤如实归为组件改动。
3. 默认额度改为按工作请求计算：最多 45 分钟总墙钟时间与 8 个实测候选版本，包含确认/打包预留，达到任一上限停止。这是操作默认值，未声称是最佳搜索预算。新请求可启动下一默认轮次，累计消耗与用户明确上限继续保留。
4. 区分比赛规则、用户限制、agent 暂定政策。非等价优化允许不同有效输出；不使用通用最小收益、最大减速或显著性门槛替代真实目标。政策修订只影响后续开发，冻结的确认交付规则不能按结果修改。
5. 缺少评分参数时保存原始分项和有价值的取舍候选，选优结论标注为暂定；交付实际代码、运行命令、指标来源、成本与局限。

## 反馈驱动的迭代闭环

入口现在明确在同一工作轮次重复“选择 → 实施 → 运行对比 → 反馈 → 下一项实施”，实验之间无需用户再次要求继续。反馈同时回答两件事：这个候选是否超过当前最好版本，以及它的机制是否值得下一次投入。

每个后继实验引用它所依据的结果，记录具体代码/流水线目标和可检验预期。结果可能导向修复、补测、深入、替换路线或组合；不能只记录“效果不好”再做一个无关小改。有效但较弱的候选若有受支持的缺失组件，可继续投入而不覆盖 incumbent；实现失败则不能否定其方法。

最终交付展示实际执行链“结果 → 反馈决定 → 后继改动 → 新结果/停止原因”。这要求记录反馈的去向，也要求真的实施评测；建议和未执行计划保持待执行状态。详细分支见 [反馈规则](../skills/competition-optimize/references/score-search.md#close-the-feedback-loop)。

下一步方案默认由 agent 根据当前实际源码、匹配的成功/失败结果及相关历史改动提出：指出代码中的限制、历史依据、具体机制、与被否定实现的区别以及验证预期，随后直接实施。已移除自动调参分支和“成功后扫描敏感参数”的指令；专门的参数搜索仅在用户明确要求时开启。方案细节见 [代码与历史驱动的优化](../skills/competition-optimize/references/score-search.md#propose-from-code-and-history)。

为提高效率和质量，新增一次有边界的侦察与候选质量门：只读取当前代码路径、匹配的历史证据和评测身份；证据足够后停止泛读。候选先检查接口、硬规则、评测/fixture 身份、产物可复现性和目标口径，必要时用经过说明的廉价阶段淘汰明显无效候选，再进入完整对比。

本次继续加入候选档案和路线切换规则：保存 incumbent、runner-up、不同路线代表、未解决机会与失败机制；用代码/配置指纹拦截换名字重试。每次结果都决定继续当前路线（exploit）还是切换表示、模型、邻域、数据或策略（explore），并记录切换依据。这样有限预算优先用于产生新信息和完整方法，而不是重复局部编辑。

## 验证范围

本次检查 skill 格式、文档链接、指令一致性和安装副本。未修改 evaluator 或重新运行旧候选；既有工具测试和历史脚本 pilot 不能证明这些指令已改善自主解题效果。

新版还需要在有可执行题目、数据和剩余额度的真实任务中试跑：核对是否实施并运行完整方法，弱结果是否推动下一次实现，交付是否有可复现产物，以及按相同评测口径比较后的实际收益。没有得分改善也应如实报告，不能把“完成实现”直接算作提分成功。
